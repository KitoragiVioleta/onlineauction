# Дослідження: Імітаційний прототип онлайн-аукціону

## Рішення 1: Standalone Java без build-системи

**Decision:** Використати пакет `onlineauction` у `src/` і компілювати його
безпосередньо `javac`, без Maven, Gradle або сторонніх бібліотек.

**Rationale:** Репозиторій не містить вихідного коду, build-файлів чи тестового
фреймворку. Це найпростіший спосіб виконати вимоги локальної командної
компіляції, відсутності зовнішніх залежностей і навчальної прозорості.

**Alternatives considered:** Maven/Gradle відхилено як зайву інфраструктуру для
12 невеликих Java-файлів; запуск через IDE відхилено конституцією.

## Рішення 2: Java 17 як цільовий рівень

**Decision:** Компілювати з `javac --release 17`; використовувати лише
стандартний API Java 17. Новіший JDK може компілювати цей код із тим самим
release-рівнем.

**Rationale:** Java 17 є поширеним LTS-рівнем, достатнім для
`BigDecimal`, `LocalDateTime`, enum, інтерфейсів і колекцій. У середовищі
доступний JDK 26, але репозиторій не має зафіксованої версії, тому явний
`--release` робить ціль сумісною та відтворюваною.

**Alternatives considered:** Java 26 відхилено через зайве звуження сумісності;
Java 8 відхилено як застарілу ціль без потреби в такому обмеженні.

## Рішення 3: Детерміновані часові дані

**Decision:** `Main` задає фіксовані `LocalDateTime` для початку, завершення та
кожної ставки й передає час у перевантажений `placeBid(..., submittedAt)`.

**Rationale:** Один запуск має показувати прийняті й відхилені ставки
однаково на кожному виконанні, без `Thread.sleep`, системного годинника чи
ручного введення.

**Alternatives considered:** Поточний час і реальне очікування відхилено як
недетерміновані та несумісні з критерієм завершення до 10 секунд.

## Рішення 4: Розподіл відповідальностей

**Decision:** `Auction` керує станом і правилами торгів, `Lot` володіє
ставками, ролі виконують операції учасників, `AcquiringService` лише імітує
оплату, а `Main` оркеструє демонстраційні сценарії.

**Rationale:** Такий поділ відповідає SRP, існуючим UML/CRC-артефактам і
дозволяє перевіряти переходи без глобального стану.

**Alternatives considered:** Єдиний великий клас сценарію відхилено через
порушення SRP; repository/database layer відхилено через вимогу in-memory.

## Рішення 5: Контракт перевірки через stdout

**Decision:** Автоматичний запуск не приймає команди користувача; перевірка
виконується за стабільними українськими повідомленнями, що позначають
переходи, прийняті/відхилені ставки, результати та симульовану оплату.

**Rationale:** Вимога визначає один демонстраційний запуск, а не інтерактивний
CLI. Стабільні маркери дають змогу перевірити результат командним рядком без
додаткової залежності від тестового фреймворку.

**Alternatives considered:** Інтерактивне меню відхилено через FR-008a;
форматований JSON відхилено як зайву складність для навчальної консолі.
